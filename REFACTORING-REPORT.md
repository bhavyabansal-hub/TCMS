# TCMS — Full Codebase Restructuring Report

**Date:** September 2026 · **Scope:** entire backend + database schema + frontend alignment
**Standards applied:** Controller → Validation → Service → Repository layering, 100% raw
SQL data access, strict naming conventions, DRY/SRP/modularity, standard response
envelope, graceful error handling, proper logging, PostgreSQL entity-named primary keys.

---

## 1. What changed (before → after)

### Architecture

| Aspect | Before | After |
|---|---|---|
| API structure | 12 monolithic `route.ts` files (up to 372 lines) mixing HTTP parsing, permissions, business rules and DB access | 4-layer architecture: every resource folder carries `route.ts` (thin Controller), `<resource>.validation.ts`, `<resource>.service.ts`, `<resource>.repository.ts` |
| Data access | Prisma ORM model calls (`db.testCase.findMany(...)`) inline in routes | **100% raw SQL** via parameterized `db.$queryRaw` / `db.$executeRaw` inside repositories only — zero ORM model calls in the API layer |
| Responses | Ad-hoc `NextResponse.json` in each route | One envelope from `src/lib/api.ts`: `ok()`, `paginate()`; errors always `{ error, details? }` |
| Errors | Mixed status codes per route (stats answered unknown actions with 200) | `ApiError` (400/401/403/404/409) thrown by services/validators, mapped by the `withApi()` boundary in controllers; unknown action = 400 everywhere |
| Validation | Inline zod in some routes, none in others | Dedicated zod validator per controller action, run BEFORE the service |
| Logging | Scattered `console.*` | `src/lib/logger.ts` — leveled structured logs (`[tcms] <time> LEVEL message {meta}`); every request logged with status + latency via `withApi()` |
| Serialization | Partial, with local copies in routes | One boundary: `src/lib/serializers.ts` maps snake_case SQL rows → camelCase API shapes, exactly once, for every entity |
| Controllers total size | ~2,476 lines | 665 lines (thin HTTP adapters) |
| New layer code | — | 37 files (repositories / services / validators) + shared infrastructure |

### Database schema (PostgreSQL)

Primary keys are no longer a generic `id` repeated on every table — each table's key is
named after its entity, and ALL tables/columns follow snake_case (SQL convention) while
TypeScript keeps camelCase via Prisma `@map`/`@@map`:

| Table (new) | Primary key (new) | Was |
|---|---|---|
| `users` | `user_id` | `User.id` |
| `refresh_tokens` | `refresh_token_id` | `RefreshToken.id` |
| `modules` | `module_id` | `Module.id` |
| `module_permissions` | `module_permission_id` | `ModulePermission.id` |
| `test_cases` | `test_case_id` | `TestCase.id` |
| `test_case_history` | `history_id` | `TestCaseHistory.id` |
| `module_review_requests` | `module_review_request_id` | `ModuleReviewRequest.id` |
| `review_requests` | `review_request_id` | `ReviewRequest.id` |
| `review_events` | `review_event_id` | `ReviewEvent.id` |
| `bugs` | `bug_id` | `Bug.id` |
| `bug_test_case_links` | composite (`bug_id`, `test_case_id`) | unchanged (already proper) |
| `task_reports` | `task_report_id` | `TaskReport.id` |
| `notifications` | `notification_id` | `Notification.id` |
| `activity_logs` | `activity_log_id` | `ActivityLog.id` |

- Columns renamed camelCase → snake_case (`full_name`, `password_hash`, `created_at`,
  `expected_result`, `steps_to_reproduce`, `flagged_fields`, `before_snapshot`, ...).
- Primary keys are **generated by the database** (`gen_random_uuid()::text`,
  PostgreSQL 13+) — application code never supplies ids.
- Foreign keys reuse the referenced PK name (`test_cases.module_id → modules.module_id`,
  `modules.parent_id → modules.module_id`).
- `prisma/database-setup.sql` was regenerated from the schema (tables → indexes →
  foreign keys, one ordered paste-into-SQL-Editor script, all 14 tables).

### API JSON contract

Every entity now carries its proper key end-to-end (DB → repository → serializer →
API → frontend): `userId`, `moduleId`, `testCaseId`, `historyId`, `reviewRequestId`,
`reviewEventId`, `moduleReviewRequestId`, `bugId`, `taskReportId`, `notificationId`,
`activityLogId` — including nested references (`author: { userId, fullName }`,
`module: { moduleId, name, parentId }`). The frontend (18 files) was swept to the new
contract; `ModuleReviewRequest._count.caseReviews` became `caseCount`.

### Frontend (DRY / component-based)

- Extracted genuinely duplicated UI into `src/components/shared/`:
  `badges.tsx` (PriorityBadge ×6 usages, StatusBadge ×14, SeverityBadge ×2),
  `detail-field.tsx` (DetailField ×15), `page-header.tsx` (×4),
  `pagination.tsx` (PaginationFooter), `state.tsx` (EmptyState/StateLoading).
- Fixed a pre-existing compile-broken bug-report form (sent undefined `expected`/
  `actual` instead of the real state fields) and a wrong color-map usage in
  review-detail.

## 2. New file map

Shared infrastructure (`src/lib/`, `src/types/`):

| File | Purpose |
|---|---|
| `src/lib/api.ts` | Response helpers (`ok`, `paginate`), `ApiError`, `withApi` error boundary + request log, `getPagination`, zod error flattening |
| `src/lib/logger.ts` | Leveled structured logger (debug/info/warn/error) |
| `src/lib/auth.ts` | Pure JWT/bcrypt/permission matrix + `requireUser()` / `ensurePermission()` (no DB access) |
| `src/lib/activity.ts` | `logActivity()` service (diff computation) + `parseJson()` — writes via repository |
| `src/lib/notifications.ts` | `createNotification()` service — preference check + repository insert + optional WS broadcast |
| `src/lib/serializers.ts` | THE snake_case→camelCase boundary for every entity |
| `src/types/sql-rows.ts` | Typed raw-SQL row shapes incl. the `<relation>_<column>` join-alias convention |
| `src/lib/server/user.repository.ts` | Shared user lookups (by id / email / first active reviewer) |
| `src/lib/server/activity-log.repository.ts` | Shared activity-log insert |
| `src/lib/server/notification.repository.ts` | Shared notification insert |

Every API resource (14 total, incl. `health` and `keep-alive`) now follows:

```
src/app/api/<resource>/
├── route.ts                    # Controller — HTTP only (withApi + validators + services)
├── <resource>.validation.ts    # zod, one dedicated validator per action (throws 400)
├── <resource>.service.ts       # permissions, business rules, side effects, serialization
└── <resource>.repository.ts    # raw SQL only (SELECT/INSERT/UPDATE/DELETE)
```

Resources: `auth`, `users`, `modules`, `test-cases`, `reviews`, `module-reviews`,
`bugs`, `task-reports`, `notifications`, `stats`, `activity-logs`, `seed`,
`keep-alive` (+ `health`). Cross-resource access always goes through the owning
resource's repository (e.g. reviews → `test-cases.repository.updateTestCaseStatus`).

## 3. Raw SQL safety rules enforced everywhere

- Values only through tagged-template parameters (`WHERE id = ${id}` → bind parameter);
  `Prisma.sql` / `Prisma.join` for dynamic fragments. No string concatenation, no
  `$queryRawUnsafe`/`$executeRawUnsafe` with user input.
- JSONB writes: `${JSON.stringify(value)}::jsonb`.
- Every `UPDATE` sets `updated_at = NOW()` (raw SQL bypasses Prisma's `@updatedAt`).
- Aggregates cast to `::int` (avoids PostgreSQL BigInt surprises).
- Case-insensitive search via `ILIKE` (search used to be case-sensitive — intentional fix).
- INSERTs never supply primary keys (DB-generated uuids).

## 4. Intentional behavior changes (beyond pure restructuring)

1. Primary keys renamed end-to-end (table above).
2. Search is now case-insensitive (`ILIKE`).
3. Unknown API actions return a consistent **400** (stats used to answer 200).
4. Notification ownership violations return **403** (used to be 400).
5. Invalid input now fails fast with 400 + field-level messages (some legacy paths
   crashed 500 mid-operation).
6. Whole seed wrapped in one transaction (atomic; legacy could leave partial data).
7. Every request is logged (method, path, action, status, latency) via `withApi()`.

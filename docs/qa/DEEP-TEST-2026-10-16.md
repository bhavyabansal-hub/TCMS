### Steps / expected / actual (quoted from the run output)

**R2-3 (S1)** — Steps: log in as a manager; `PUT /api/users?id=<own id> {"role":"vp"}`.
Expected 403 (a role without `manage_permissions` must not reach VP). Actual 200, row role=`vp`
(role-flows step 5.4). Cause: `src/app/api/users/users.service.ts:112-128` has no self-change /
role-ceiling check; `createUser` also allows any role (`:78`).

**T1-1 (S2)** — Steps: bug with severity `low`; drag it to In Progress (sends `{status, expectedUpdatedAt}`,
`src/components/views/bugs.tsx:130`). Expected severity stays `low`. Actual `severity=medium`
(toggle check E2; role-flows step 2.6). Cause: `updateBugSchema = createBugSchema.partial()`
(`src/app/api/bugs/bugs.validation.ts:26`) keeps `severity.default('medium')` (`:16`) under zod 4.

**T1-2 (S2)** — Steps: as developer, open a bug → Edit → change status → Save. Expected 200 (triage is allowed for
`create_bug`, `bugs.service.ts:160`). Actual 403 "Only roles with assign-bug rights…". Cause: dialog always sends
`assignedToId` (`bugs.tsx:781-784`); service checks `!== undefined` instead of "changed" (`bugs.service.ts:163`).

**R2-1 (S2)** — Steps: QA submits → manager `needs_revision` → QA edits + resubmits (cycle 2) → manager approves
cycle 2 → verdict `failed` on cycle 1. Expected the resubmit closes cycle 1; verdict on it 400/409. Actual cycle 1
`in_progress`, queue shows `["cycle2:pending","cycle1:in_progress"]`, verdict 200, case `needs_revision`.
Cause: `reviews.service.ts:229` keeps needs_revision open; `test-cases.service.ts:266-282` never closes the old cycle.

**R2-2 (S2)** — Steps: as QA `POST /api/bugs {…, assignedToId:<developer>}`. Expected 403 (as for reassign).
Actual 200, `assigned_to=developer`, developer gets `bug_assigned`; UI picker enabled. Cause:
`bugs.service.ts:95-105,134-143` checks only `create_bug`; picker ungated `bugs.tsx:518-530`.

**T1-3 (S3)** — `PUT /api/test-cases?id {title}` on a P1 case with tags → `priority=P2 tags=[]`
(`test-cases.validation.ts:22-27`). **T1-4 (S3)** — `PUT /api/task-reports?id {notes}` → `tasks=0 total=0`
(`task-reports.validation.ts:38,42`). **R2-4 (S3)** — submit-review on an approved case → 200, status
`in_review` (`test-cases.service.ts:249-264`, no status check). **R2-5 (S3)** — QA opens `/test-cases/<id>`
after needs_revision with flags → flags not shown (`test-case-detail.tsx:300-312`). **R2-6 (S4)** — bulk approve,
author = requester → 2 identical `review_approved` rows (`module-reviews.service.ts:244`). **T1-5 (S4)** —
`permissions.service.ts:85-90` always returns `source:'override'`. **DOC-T1-6 (S3)** — `docs/architecture/auth-and-permissions.md:148, 184, 194, 199, 201, 202, 210`.

Common root cause for T1-1, T1-3, T1-4: `createXSchema.partial()` under zod 4 still applies
`.default()` values, so omitted fields are overwritten on every partial update.

## 3. Observations (allowed by the code today — owner decides, not counted as bugs)

- Any `create_bug` holder may change the status of any bug, including closing it (`bugs.service.ts:160`).
- No notification on a bug status change (the reporter is not told).
- Every work-log save notifies every active vp/manager/product (`task-reports.service.ts:160-186`).

## 4. Harness findings (not app bugs)

- `scripts/lib/db-guard.mjs`: in long runs Prisma can move queries to another pool connection while the first
  one keeps the `tcms_verify` lock, so `assertLockOwned()` can report a false "lock lost". Both new scripts use a
  lock-holder watchdog (lock held by one of this process's connections; re-acquire if freed). A proper fix belongs
  in `db-guard.mjs` (pin one connection) — dev decision.
- One flaky UI readiness wait (toggle run 4, see §1).
- Memory: the role-flow script now runs one browser context at a time (OS killed run 1 at low RAM).
